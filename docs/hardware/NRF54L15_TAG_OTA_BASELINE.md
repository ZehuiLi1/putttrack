# nRF54L15 Tag OTA baseline

## Decision

Use SWD/DAPLink for initial commissioning and recovery. Use signed BLE OTA for
normal application releases after the boot chain has been validated.

DAPLink remains required for:

- first installation of MCUboot, the partition layout and trust material;
- recovery from a damaged bootloader, incompatible partition layout, lost key,
  or failed security provisioning;
- low-level debug and production fault analysis.

OTA can subsequently update the application, but it must not be treated as the
only recovery path.

## Development baseline

The first build uses Nordic/Zephyr's SMP server sample rather than PuttTrack
application code. This isolates four facts:

1. MCUboot starts correctly on the Tag;
2. the Tag advertises the SMP BLE service;
3. a signed update can be uploaded and test-booted;
4. an unconfirmed or broken image reverts to the previous image.

Build with:

```bash
scripts/nrf54l15_tag/build_ota_smoke.sh
```

The command above deliberately permits a compile-only smoke build with Nordic's
insecure debug key and prints a warning. Any image intended for a physical Tag
must provide an explicit key stored outside the repository:

```bash
SIGNING_KEY=/absolute/private/key.pem \
BUILD_DIR="$PWD/build/nrf54l15-tag-ota-labkey" \
scripts/nrf54l15_tag/build_ota_smoke.sh
```

Expected output includes a full first-install image and a DFU archive such as
`first_install.hex` and `dfu_application.zip`. The full image combines MCUboot
with the signed slot-0 application. Do not flash a child image selected only by
filename.

The current Tag layout is 68 KiB MCUboot, two 696 KiB application slots and
64 KiB settings storage. The smoke image exposes SMP over BLE only; UART and
shell transports are disabled because the Tag has no debug UART selected.

## Security and lifecycle rules

- Never ship or commit the MCUboot private signing key.
- Do not rely on an autogenerated key outside a disposable lab build.
- Freeze the partition map before collecting long-lived devices in the OTA
  fleet. Ordinary OTA is not a safe partition migration mechanism.
- Require signed images, monotonically increasing release versions and an
  allowlisted hardware/board identity.
- The generic lab sample uses encrypted BLE SMP access with
  `CONFIG_MCUMGR_TRANSPORT_BT_PERM_RW_ENCRYPT=y`. Its signed image check prevents
  booting untrusted firmware, but this is not sufficient authorization for a
  product.
- Product firmware should add a workable authorization mechanism (for example,
  physical-button update mode, passkey/OOB pairing, or an application-level
  challenge) and then use authenticated SMP access. Do not set
  `CONFIG_MCUMGR_TRANSPORT_BT_PERM_RW_AUTHEN=y` without implementing the required
  pairing callbacks; the management service would become unreachable.
- Boot a new image in test mode. Confirm only after application startup,
  persistent storage, sensors, BLE control and watchdog health checks pass.
- Reboot without confirmation on failure so MCUboot reverts automatically.
- Keep a physical SWD recovery fixture and a known-good full image.

## Safe bring-up gates

Do not overwrite the factory image until all of these are retained:

- official factory/recovery firmware for the exact Tag revision;
- Tag hardware revision and current firmware identity;
- complete first-install HEX SHA-256;
- update ZIP SHA-256;
- fixed signing-key identity/public-key hash;
- partition report and MCUboot configuration;
- a verified DAPLink recovery command.

The first physical OTA test should use two deliberately different application
versions with a visible LED/advertising version marker. Test success, deliberate
non-confirmation/revert, corrupt-signature rejection and interrupted upload.

The repository's first positive OTA variant sets image version `0.0.1+0` and
advertises as `PuttTrack-OTA-v2`. Build it with the same signing key and add:

```bash
VARIANT_CONF="$PWD/firmware/nrf54l15_tag_ota/ota_test_v2.conf"
```

## First positive OTA result

The physical Tag passed the complete BLE OTA flow on 2026-09-02 using the XIAO
nRF52840 Sense as the USB HCI controller:

1. the signed `0.0.1+0` image was uploaded to slot 1 while confirmed `0.0.0`
   continued running in slot 0;
2. the slot-1 hash reported by the Tag exactly matched the locally verified
   MCUboot image digest;
3. the image was marked for test and the Tag rebooted as `PuttTrack-OTA-v2`;
4. `0.0.1` reported active but unconfirmed, as expected for a test boot;
5. it was confirmed remotely, then survived a second reboot as active and
   confirmed.

With nrfutil mcu-manager 0.11.0, upload the signed BIN directly. That version
rejects this build's single-image ZIP on the BLE transport even though its help
mentions multi-image ZIP packages:

```bash
nrfutil mcu-manager ble \
  --hci-serial-port /dev/cu.usbmodem101 --timeout 30 \
  image-upload --device-name PuttTrack-OTA-v2 --scan-timeout 10 \
  --pair --secure-connection \
  --firmware build/<build-dir>/smp_svr/zephyr/zephyr.signed.bin \
  --image-number 0
```

After upload, use `image-list`, `image-test --hash <image-hash>`, `reset`, and
finally `image-confirm --hash <image-hash>`. Do not confirm merely because the
device advertises: perform the application's required health checks first.

## Optional Mac BLE controller

`nrfutil mcu-manager ble` on macOS uses a Nordic controller exposing H:4 over a
serial port. The connected Seeed XIAO nRF52840 Sense can provide that controller.
Build its USB CDC HCI firmware with:

```bash
scripts/nrf54l15_tag/build_xiao_hci_usb.sh
```

The UF2 output is under
`build/xiao-nrf52840-hci-usb/hci_uart/zephyr/zephyr.uf2`. Installing it replaces
the XIAO's current application, but leaves its UF2 bootloader available for
recovery. Double-reset the XIAO to mount the bootloader drive before copying the
UF2. This step is not needed when using the mobile Device Manager app directly.

## Production direction

For the research Tag, MCUboot-only with internal primary/secondary slots is the
lowest-complexity starting point. NSIB + MCUboot, KMU-backed verification,
runtime key revocation and encrypted images should be evaluated before a custom
Ball production security freeze. They add useful protection but also add
irreversible provisioning and recovery complexity; they should not be enabled
casually on the first Tag.

## Repository-owned application result

The generic SMP smoke image has now served its purpose. The physical Tag runs
the repository-owned application in `firmware/nrf54l15_tag_app/` while keeping
the same MCUboot partition map and lab trust root.

Firmware `0.1.7+0` passed this sequence on 2026-09-02:

1. local Ed25519 signature verification;
2. encrypted BLE upload through the XIAO nRF52840 USB HCI controller;
3. MCUboot test selection and reboot;
4. stable hardware identity, new boot identity, both IMUs ready and no sensor
   errors;
5. status verification of the 50 Hz stream, both 100 Hz sensor ODRs, ±2g
   ADXL367 range, ±16g BMI270 acceleration range and ±2000 dps gyroscope range;
6. atomic freeze and 16-block retrieval of 1024 samples/20.46 seconds with one
   capture ID, measured 50.0 Hz source timestamps, zero sequence gaps and 100%
   validity;
7. remote confirmation and a further reboot;
8. `image-list` still reported `0.1.7` active and confirmed, followed by a
   second complete 1024-sample frozen-history capture after reboot.

The signed image digest reported by imgtool and the Tag was:

```text
4d1290ed6c23812655705275ca4fb7bb7db8fd917c9baf53bb3d9d8df9deccad
982f138fab523c3e1bddf4fde4548e92ea01d82275f45bccb257621f7efe7ad9
```

This establishes OTA as the normal application-update path. DAPLink remains a
commissioning/recovery tool and is not required for ordinary firmware changes.

## Confirmed adaptive-power update history

Firmware `0.1.9+0` subsequently passed the same guarded OTA flow on the physical
Tag. It was uploaded while confirmed `0.1.7` remained recoverable, test-booted
without confirmation, and exercised through full-rate capture, forced idle,
automatic idle, slow-advertising reconnect and physical motion wake. Only then
was it confirmed. A further reset reported `0.1.9` active and confirmed, a new
boot ID, both IMUs ready and zero sensor errors.

Its MCUboot image digest is:

This established the first confirmed adaptive-power baseline.

Firmware `0.1.10` was later test-booted but deliberately left unconfirmed. It
proved CR2032 idle and slow-advertising management access, then became
undiscoverable after a management disconnect. A physical reset correctly
rolled it back to confirmed `0.1.9`, demonstrating that the recovery contract
still worked.

Firmware `0.1.11` added retryable advertising-start work and corrected the
active keep-awake threshold using recorded battery stationary data. It passed
signed BLE upload and test boot while the Tag was powered from CR2032, automatic
idle, six consecutive idle reconnects, physical wake, return to idle, remote
confirmation and reset. After the reset it again entered idle and passed two
more slow-advertising reconnects. It became the confirmed active image, with
MCUboot digest:

```text

ecfbea9f2de1300376c9ba4ce77660789b8d3c7b59c236a2097974daa2b67672
```

Firmware `0.1.13` subsequently replaced polling idle with the physically
verified ADXL367 INT1 route on nRF54L15 P0.03. It was uploaded and test-booted
with confirmed `0.1.11` preserved for rollback, then exercised through extended
idle, two repeated interrupt wake/re-sleep cycles, confirmation and a
post-confirm reset/idle cycle. Sensor, power-management and advertising errors
remained zero. The active image is now `0.1.13`, confirmed, with MCUboot digest:

```text
ddededad6a34dda066d4f7471de4c1647ad2564a4b2856559c1f23a41aac40b1
8c5e6f0d12a28bb14254cd4983aee368fdf40ef8cd54e5af335ee57ececc223f
```

The intermediate `0.1.12` image was intentionally left unconfirmed and rolled
back after its second idle cycle exposed a referenced-activity ordering defect.
This preserved the guarded OTA contract while allowing `0.1.13` to correct and
revalidate the sequence.

Future ordinary application updates use BLE OTA; DAPLink is retained only for
first commissioning or recovery from a damaged boot/update path.
