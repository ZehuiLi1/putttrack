# IMU 下一阶段工程计划 — 2026-09-04

## 决策

当前同一颗 Ball、同一操作者、同一天和相近环境下的数据，已经足够进入
检测器工程阶段。现在暂停重复采集，不再为了增加样本数量重复相同动作。

已经版本化的关键类别包括：

- 10 次严格不离地的触碰、转动和轻微挪动；
- 10 次滚动中拿起；
- 10 次静止起步拿起、携带和轻放；
- 10 次静止起步拿起、携带和低高度随手丢下；
- 11 次轻推杆（其中一份明确保留为混合障碍物样本）；
- 10 次推杆后边轨碰撞；
- 11 次滚过小台阶（含一份混合障碍物样本和干净替代样本）；
- 86 次正式滚轮速度、方向、加速、减速与边界表征；
- 更早的静止、人工滚动、拿起、普通推杆与诊断数据。

这些数据足以实现和挑战一个研究检测器，但仍不足以声称产品准确率。

## Phase A — 下一项必须完成的软件工作

实现从原始 JSONL 直接运行的、可重复的
`pickup_detector_v0_stationary_start` 评估链：

```text
raw JSONL
  -> 身份/连续性/传感器/GO marker 校验
  -> GO 前静止基线
  -> onset 检测
  -> 姿态传播与竖直冲量
  -> 1 秒 gyro 能量和旋转轴一致性
  -> PICKUP / NOT_PICKUP / UNKNOWN
  -> 分类别、分 session 的报告
```

实现范围：

1. `src/putttrack/motion/pickup.py`
   - 严格实现 `configs/research/pickup_detector_v0.json`；
   - 从配置读取全部阈值，不在代码里复制隐藏阈值；
   - 对缺少静止基线、GO marker、样本、连续性、健康信息或发生 BMI270
     特征窗口削顶的输入返回 `UNKNOWN`；
   - 滚动起步继续返回 `UNKNOWN_UNSUPPORTED_PATH`，不得套用静止模型。
2. `tools/evaluate_pickup_detector.py`
   - 直接读取实验 manifest 和原始 JSONL；
   - 输出逐 episode 的特征、判定、延迟、UNKNOWN 原因和配置哈希；
   - 按 label、session、操作者、Ball 和表面汇总；
   - 输出混淆矩阵、pickup precision/recall、负例误报率和 95% 置信区间；
   - 不允许随机拆分同一次连续动作的窗口。
3. `tests/test_pickup_detector.py`
   - 覆盖静止起步拿起、不离地处理、单轴滚动、滚动中拿起、重复轻敲、
     缺失基线、时间回退、丢样、传感器错误和削顶；
   - 固定小型原始记录 fixture，确保数值结果可复现；
   - 确认所有输出始终为 `authority=false`。
4. 生成一次完整、不可手工修改的离线报告
   - 正例：`pickup_carry`、`pickup_drop`；
   - 静止起步负例：`handling`、`putt_gentle`、边轨碰撞和小台阶；
   - `rolling_pickup` 单独报告为暂不支持，不计入静止模型准确率；
   - 诊断失败、混合标签和无动作样本单独列出，不混入干净真值指标。

## Phase A 合并门

满足以下条件即可合并研究工具，不需要先补更多同环境数据：

- 原始 JSONL 到最终判定可用一条命令重现；
- 配置版本和 SHA-256 出现在每份输出中；
- 相同输入重复运行产生字节稳定的 CSV/JSON；
- 单元测试覆盖所有 fail-closed/UNKNOWN 路径；
- 报告明确区分干净、混合、诊断和不支持样本；
- 不修改冻结 V0 阈值；
- 不连接 Gameplay，不产生处罚或计分权威。

## Phase B — 只按失败结果定向处理

完成 Phase A 后再决定是否补数据：

- 如果某类负例误报，只增加该类及其边界变体；
- 如果拿起漏报，先检查姿态传播、onset、窗口和削顶，再决定是否建立 V1；
- V0 一旦失败也不回改；创建新 detector ID，并留一批新的未看数据验证 V1；
- 当前不使用神经网络。先比较可解释规则、逻辑回归和小型树模型；只有在
  多 Ball、多操作者、多场地的数据规模明显扩大后才重新评估时序神经网络。

Phase A 运行结果只允许产生 `PICKUP_SUSPECTED` 研究证据。即使结果很好，
也不能自动判本洞失效。

## Phase C — 产品声明前必须补的独立物理证据

这部分暂不立即采集，等软件指出具体盲点后再进行：

1. 至少一个新的日期和 boot/session，采集前冻结将被测试的检测器版本；
2. 至少一个不同操作者；
3. 第二颗 Tag/Ball；
4. 至少两种代表性表面和不同初始朝向；
5. 对检测器失败最多的动作类别做定向边界样本；
6. 有实际杯洞后，采集杯口、落杯、弹出、停住，并用光电传感器或视频提供
   独立真值。

独立批次必须整批报告，不能挑选表现好的 episode。产品级自动失效策略仍需
单独确定可接受的 precision、误报上界和 UNKNOWN/review 行为。

## 与整机路线的衔接

IMU Phase A 可以与物理 Tee/Cup 工作并行：

- Tee：固定 PN532，负责近场 presence 和进入球道；
- Cup：光学入杯候选 + PN532 确认当前 active Ball；
- Ball：只提供带来源的运动证据，不单独负责计分；
- Edge/Game：持有球道、session、epoch 和最终规则权威。

在检测器离线报告完成后，下一项产品价值最高的里程碑仍是把实际 Tee/Cup
接入现有 one-hole 软件路径，完成一次真实自动单洞闭环。

## 当前暂停项

- 不再重复同一天、同一人、同一颗球的相同动作；
- 暂不要求较重/远距离推杆；现有场地和 BLE 实时范围不适合提供干净真值；
- 暂不把阈值写入 Tag 固件或 Gameplay；
- 暂不训练神经网络；
- 暂不恢复 Channel Sounding；
- 没有电流仪器前，不声明最终电池寿命。

## 完成顺序

1. 原始数据驱动的冻结 V0 evaluator；
2. 全量离线报告和失败样本审计；
3. 只对暴露出的缺口补定向数据，或建立 V1；
4. 独立日期/操作者/第二颗 Ball 的盲测；
5. 物理 Tee/Cup 自动单洞闭环；
6. 通过独立验证后，才讨论是否让高置信度拿起影响本洞规则。
